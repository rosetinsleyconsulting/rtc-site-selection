 Multi-tenant accounts + admin tools for the Lowlu 
 site-selection app

 Context

 The app (src/main.jsx) is currently a pure static frontend:
 one CSV (Lowlu's site list) is baked in at build time, there's
 no backend, no accounts, and site accept/dismiss status is
 saved to the browser's localStorage only. It's being turned
 into a product served to multiple clients, each needing their
 own isolated map/dataset, with per-user login and a way for an
 administrator (Eilish) to control who can see which client's
 data.

 Decisions already confirmed with the user:
 - Auth: Clerk. Note: the repo's bundled clerk-auth skill
   assumes Replit Agent-only provisioning tools
   (setupClerkWhitelabelAuth, etc.) that aren't available in
   this session, so this plan wires up standard Clerk
   (@clerk/clerk-react + @clerk/express) using API keys from
   the user's own Clerk account, added as Replit secrets.
 - Data model: separate workspace per client (not a shared
   dataset). Each workspace has its own site list; users are
   granted access to specific workspaces by an admin.

 Past-incident lessons that shape this design (saved to memory,
 applied below): Clerk invite links must land on a route that
 renders Clerk; user auto-linking must be race-safe; MapLibre's
 worker needs the existing Vite bundling fix (already present,
 untouched); authenticated GET routes need explicit no-store
 caching; verify prod behavior via build output/curl, not
 assumptions.

 Architecture

 Single-origin Express server replaces the plain vite dev/build
 split — this also sidesteps the whole class of
 Clerk-proxy/CORS/cookie-mismatch issues from the past-incident
 notes, since there's no cross-origin split between frontend
 and API:

 - Dev: server/index.js creates a Vite dev server in middleware
   mode and mounts it, so npm run dev still serves the SPA
   with HMR on port 5000, plus /api/* routes.
 - Prod: same file serves dist/ as static files (from vite
   build) and the same /api/* routes.
 - Clerk's browser SDK talks to Clerk's CDN/API directly (no
   proxy needed — proxying is only for Replit-managed custom
   domains, not applicable here). Auth is cookie-based end to
   end, per Clerk's standard web flow.

 Database (Postgres, already provisioned via DATABASE_URL):
 Drizzle ORM + drizzle-kit for schema/migrations.

 Tables:
 - users (id, clerk_user_id unique, email, name,
   is_platform_admin bool default false, created_at) —
   JIT-provisioned on first authenticated request via an atomic
   INSERT ... ON CONFLICT (clerk_user_id) DO NOTHING
   (race-safe, no check-then-insert). If the email matches
   PLATFORM_ADMIN_EMAILS (env var, comma list — seeded with
   eilish@rosetinsleyconsulting.com), the new row is created as
   is_platform_admin = true.
 - workspaces (id, name, slug unique, created_at)
 - memberships (user_id FK, workspace_id FK, created_at) —
   existence = access. No per-workspace roles for v1;
   is_platform_admin is the only elevated role, matching what
   was actually asked for.
 - sites (id, workspace_id FK, + the 15 existing CSV columns:
   type, borough, site_name, category, priority, footprint_m2,
   spare_land_on_title_m2, voa_rateable_value,
   voa_match_confidence, nearby_planning_applications,
   nearby_parking, data_confidence_notes, spare_area_comments,
   lat, lon)
 - site_statuses (site_id FK unique, status
   enum('new','accepted','dismissed') default 'new', updated_by
   FK users, updated_at) — shared per workspace, matching the
   tool's existing "shared shortlist workspace" framing; any
   member can update it, not just admins.

 API routes (all behind clerkMiddleware() + JIT-provision-user
 middleware):
 - GET /api/me — local profile, isPlatformAdmin, and list of
   workspaces the user can access (id, name, slug).
 - GET /api/workspaces/:id/sites — sites + statuses for one
   workspace (membership or admin required). Cache-Control:
   private, no-store set explicitly.
 - PATCH /api/workspaces/:id/sites/:siteId/status — update
   status (membership or admin required).
 - POST /api/workspaces/:id/import-local-statuses — one-time
   best-effort migration: if the workspace has zero statuses
   set and the client posts its old lowlu-statuses localStorage
   blob, apply it. Protects Eilish's existing testing data
   with near-zero added complexity.
 - Admin-only (is_platform_admin required):
   - GET/POST /api/admin/workspaces — list, and create (name +
     slug + pasted/uploaded CSV text, parsed with the existing
     parseCSV logic moved to src/lib/parseCsv.js and reused by
     both client and server).
   - GET /api/admin/users — list local users with their
     memberships.
   - POST /api/admin/users/invite — {email}, calls Clerk's
     Backend SDK invitations.createInvitation with redirectUrl
     pointing at /sign-up (never /, per the invite-routing
     lesson).
   - POST /api/admin/users/:userId/memberships / DELETE
     .../memberships/:workspaceId — grant/revoke workspace
     access.
   - PATCH /api/admin/users/:userId — toggle isPlatformAdmin.

 Frontend (src/): split the current single main.jsx into:
 - main.jsx — entry: <ClerkProvider> + react-router-dom routes
   for /, /sign-in, /sign-up, /admin.
 - App.jsx — today's map/list/filters UI (from current
   main.jsx), changed to fetch sites from
   /api/workspaces/:id/sites instead of the build-time CSV
   import, and to PATCH status changes instead of writing
   localStorage. If the user belongs to more than one
   workspace, a small switcher appears in the sidebar; exactly
   one auto-selects it; zero shows a "no access yet" message.
 - AdminPage.jsx — workspaces list/create (with CSV
   paste/upload), users list/invite, per-user membership +
   admin-toggle controls.
 - lib/parseCsv.js — the existing parseCSV/fields logic,
   extracted so both the admin CSV-import endpoint and any
   client-side preview can share it.
 - lib/api.js — fetch wrapper defaulting to cache: 'no-store'
   and credentials: 'include'.

 Sign-in/sign-up pages use Clerk's <SignIn/>/<SignUp/>
 components directly (lightly themed to match the app's
 existing dark sidebar palette from index.css, not a full
 custom auth UI).

 Setup the user needs to do

 Before this can run, the user must create a Clerk application
 (clerk.com) and add two secrets in Replit: CLERK_SECRET_KEY
 and VITE_CLERK_PUBLISHABLE_KEY. I'll pause and give exact
 instructions for this once implementation starts, since the
 app can't boot without them.

 Implementation steps

 1. npm install express @clerk/express @clerk/clerk-react
    @clerk/backend pg drizzle-orm react-router-dom + npm
    install -D drizzle-kit.
 2. Drizzle schema (server/db/schema.js) for the 5 tables
    above; drizzle.config.js pointed at DATABASE_URL; run
    drizzle-kit push to create them.
 3. server/index.js + server/routes/*.js implementing the API
    above, JIT user provisioning, and the dev/prod
    Vite-middleware split described in Architecture.
 4. server/seed-lowlu.js — one-off script: parses attached_asse
    ts/0_lowlu_final_sites_export_1787904911415.csv via
    lib/parseCsv.js, creates the "Lowlu" workspace, inserts its
    sites. Run manually once, not wired into app startup.
 5. Rewrite src/main.jsx → main.jsx + App.jsx + AdminPage.jsx +
    lib/ as described.
 6. Update package.json scripts: "dev": "node server/index.js",
    "build": "vite build", "start": "NODE_ENV=production node
    server/index.js".
 7. Add a [deployment] block to .replit (build = npm run build,
    run = npm run start) so Replit's Publish flow works for
    this now-fullstack app — currently absent.
 8. Manually flag the effective outcome: after Eilish signs up
    once through the real app, her users row auto-gets
    is_platform_admin = true via PLATFORM_ADMIN_EMAILS, and
    I'll grant her Lowlu membership via the admin UI itself
    (dogfooding it) rather than a manual SQL step.
