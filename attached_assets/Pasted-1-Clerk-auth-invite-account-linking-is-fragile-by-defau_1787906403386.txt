1. Clerk auth — invite/account-linking is fragile by default

- Clerk's invite ticket links only work if they land on a route that actually renders Clerk (e.g. /sign-up), never a marketing/landing page — a ticket sent to / gets silently dropped with no error.
- If the app proxies Clerk's Frontend API (e.g. at /api/__clerk/*), double check every invite/ticket URL actually resolves to that proxied path, not a bare /v1/tickets/accept. A registration mismatch here fails silently: user gets a working session but the invitation never flips to "accepted."
- If linking Clerk users to your own DB user table, don't assume the auto-link path is exercised or working just because it exists in code — test it end-to-end with a real invite, not just by inspecting the code.
- Watch for races: if multiple client requests can trigger "create user if not exists" in parallel (e.g. dashboard firing several first-load queries), guard with an existence check + retry, not just try/catch on insert.

2. Database schema — check FK/PK assumptions before wiring auth-linking code

- If migrating from Supabase Auth to Clerk (or any auth swap), check whether existing tables have a user_id column that's a primary key with a foreign key into the old auth table (e.g. legacy auth.users). That column can't be made nullable and can't take an arbitrary UUID — any new auto-link insert needs a real backing row in the old auth table first (find-or-create it), not just the new provider's user id.
- Add rollback logic: if you create a linking row (e.g. a legacy auth user) as a side effect and the subsequent insert fails, clean up the orphan rather than leaving it dangling.
- When paginating admin-side listing calls against Supabase auth (auth.admin.listUsers), don't cap at the default page size (1000) — paginate fully or you'll silently miss rows.

3. Map rendering (MapLibre GL) — production build gotcha

- MapLibre's Web Worker script does not get bundled by Vite by default. It resolves the worker via new URL('./maplibre-gl-worker.mjs', import.meta.url), which works in dev (files served straight from node_modules) but Vite/Rollup won't detect or emit it in a production build. Symptom: map works perfectly in Replit's dev preview, but in production the basemap renders and fitBounds() still works (that's computed client-side, pre-worker), yet no vector/GeoJSON data ever draws — with zero console errors.
- Fix requires two parts:
  a. Explicitly import the worker with Vite's ?url suffix and call maplibregl.setWorkerUrl(...) at module scope before creating any Map instance.
  b. That alone isn't sufficient — the worker file itself has a hardcoded relative import to maplibre-gl-shared.mjs, which Vite's ?url copy doesn't rewrite or bundle. Add a writeBundle plugin in vite.config.ts that copies that shared chunk into the build output under its exact unhashed filename, next to the worker.
- Verify by inspecting the actual dist/public/assets/ output for both files — don't trust "no console error" as proof the map is fully wired in prod.
- General lesson worth carrying forward: any library that lazily loads a worker/wasm/worklet at its own runtime (not through a static import Vite can trace) is a candidate for this exact silent prod-only failure. Check built output directly when something "works in dev, not prod" with no visible error.

4. API caching — private/per-user GET endpoints need explicit no-store

- Express's default res.json() auto-generates a weak ETag. Combined with a plain fetch() (no cache option) on the client, a browser 304 revalidation returns no body, and if your fetch wrapper treats 304/204/205 as "no content" → null, private per-user data silently disappears with no server error and no client exception.
- For every authenticated GET route returning per-user/per-workspace JSON: set res.set("Cache-Control", "private, no-store") server-side and pass cache: 'no-store' client-side. Check this per route — fixing it on one endpoint doesn't mean a sibling endpoint (e.g. a "list" endpoint next to a "detail" endpoint) got the same treatment.

5. Replit deploy semantics

- "Publish" ships a real git commit of current state — if you keep editing after publishing, production stays on the old commit until the next publish. Before publishing, confirm git status is clean and git log -1 is the commit you intend to ship.
- To verify a live bug without browser access: curl -s -D - -o /dev/null <url> against the production origin gives real headers (Cache-Control, Last-Modified, status) — useful for confirming routing/health and whether a deployed bundle actually postdates a fix commit.
- Don't trust JS/CSS bundle hash comparisons as a "is my fix live" signal — local rebuilds can produce different hashes for identical source (bundler non-determinism). Instead curl the deployed bundle and grep for a string literal unique to your fix.
- If Supabase is shared across dev/prod in this environment (only Clerk has separate pools), a throwaway Node script run against the workspace's SUPABASE_URL/SUPABASE_SECRET_KEY can directly inspect/verify production data without needing a live user session — good for ruling data problems in/out before suspecting code.

6. Debugging approach worth repeating

When something looks broken with zero console errors and no failed requests the app itself initiates, suspect either (a) a caching/304 issue silently nulling out a response, or (b) a bundler asset-emission gap for something a third-party library loads dynamically by relative path at its own runtime. Both failure modes in this project produced identical-looking symptoms ("works in dev, broken in prod, no errors") but had completely different root causes — verify against actual network traces and actual build output rather than guessing from symptoms alone.
